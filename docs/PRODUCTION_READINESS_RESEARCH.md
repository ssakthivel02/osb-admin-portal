# Production Readiness Research

Status: Research complete; implementation not yet production-ready.

## Verified current repository state

The repository is presently a documentation scaffold. No executable React/Vite application, lockfile, test suite, CI workflow, API configuration or deployment artifact has yet been verified in this repository.

## Official implementation requirements

### React authentication with Microsoft Entra ID

Microsoft's current MSAL guidance requires a `PublicClientApplication` instance to be initialized before other MSAL APIs are invoked. React components that use authentication must be wrapped by `MsalProvider`. Token acquisition must use the configured application scope; Microsoft Graph `User.Read` should not be requested unless the portal genuinely calls Microsoft Graph.

Implementation consequences:

- initialise MSAL asynchronously before rendering the authenticated application;
- validate tenant ID, client ID, redirect URI and API scope at startup;
- use session storage unless a formally approved threat model requires another cache;
- do not log access tokens, ID tokens or personal claims;
- enforce the same roles in the API/database layer, not only in React routes.

### Vite production hosting

A production Vite build is generated with `vite build`, normally into `dist`. `vite preview` is only a local preview server and must not be treated as production hosting.

Implementation consequences:

- production deployment is blocked until `npm ci`, lint, type-check, tests and build pass;
- SPA route fallback must be configured by the selected host;
- the correct Vite `base` must be selected for a custom domain or repository sub-path;
- deployment should publish only the immutable `dist` artifact generated by CI.

### GitHub Pages

GitHub Pages can host the static portal after a build step, but it does not provide the secured SQL/API backend. GitHub Actions must build and publish `dist`. An authenticated editorial portal should not expose internal Dataset B information through public static assets.

Recommended use:

- suitable for a public documentation site or a UI shell that calls a separately secured API;
- not sufficient by itself for the editorial database, DAB runtime, secrets or server-side authorisation.

### Data API Builder

Microsoft documents deployment of Data API Builder to Azure App Service, which provides TLS, custom domains, scaling, monitoring and Microsoft Entra integration. A reachable supported database and .NET 8 or later are prerequisites.

Production conditions:

- validate the exact installed DAB configuration schema and version;
- expose only approved entities and stored procedures;
- keep Dataset B and internal editorial notes inaccessible to anonymous users;
- restrict canonical writes to reviewed stored procedures rather than generic table CRUD;
- configure CORS per environment;
- obtain identity/roles from trusted authentication context rather than client-supplied fields;
- enable health, logging, monitoring, rate controls and secret injection through the hosting platform.

## Recommended target topology

1. Frontend: React/Vite static application hosted through Azure Static Web Apps, App Service static hosting, or GitHub Pages for a non-sensitive shell.
2. Authentication: Microsoft Entra ID/MSAL.
3. API: Data API Builder on Azure App Service or Azure Container Apps.
4. Database: SQL Server 2022/Azure SQL reachable only from the API tier.
5. Secrets: Azure Key Vault or platform-managed configuration.
6. Monitoring: Application Insights/Azure Monitor plus structured request and correlation IDs.
7. Deployment: pull-request quality gates, immutable build artifact, controlled production promotion and rollback.

## Release gates

Production is blocked until all of the following are evidenced:

- executable React 19/TypeScript/Vite repository;
- committed dependency lockfile;
- strict environment validation;
- successful MSAL initialisation and token acquisition;
- typed API client against confirmed DAB contracts;
- server-side RBAC and Dataset B isolation;
- lint, type-check, unit/integration tests and production build passing in CI;
- accessibility and security review;
- deployment workflow and environment secrets configured;
- production URL health check and authenticated smoke test;
- rollback instructions and tested recovery path.

## Decision

Do not move this repository to production yet. The correct immediate action is to implement and verify the first executable vertical slice on a review branch, then enable a preview deployment. Production promotion should follow only after all release gates pass.
